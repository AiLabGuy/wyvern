# Wyvern security review report

This is the report of the review done before the first public release, v0.1.0. Plain statement of what it is and is not:

- **All code in this repository was generated by AI** under human direction (see [AI-DISCLOSURE.md](../AI-DISCLOSURE.md)). The review below was also done by AI agents.
- The review was **an automated multi-agent sweep**: several AI agents read the code, one wrote a threat model, and the findings were fixed and tested. **No third party audited this code.** Nothing here says Wyvern is secure. It says what was looked at, what was found, what was changed, and what is known to remain.
- The build under review is the first public build, version 0.1.0. The internal working build was number 206. The sweep fixes below were merged on top of it, and that merged tree is what this repository contains (internal build label 207).

## Method

1. A read-only threat-model review of build 206 by one agent (attack-surface map: untrusted input to privileged action).
2. Two parallel code-review agents: S1 (web content: WKWebView, navigation, downloads, permissions, address bar, terminal tab, Web Inspector) and S2 (network and parsers: updater, block-list fetcher and parser, bookmark and session parsers, file storage, entitlements, dependencies).
3. A follow-up agent (S3) for the remaining items from the threat model.
4. A visual-stability review (view re-parenting, layout loops, constraint conflicts), since flashing and artifacting also hide bugs.
5. Fixes were written by the agents and merged. The unit test suite was run on macOS after every merge (391 tests, 0 failures at the final merge of the security fixes).
6. A first launch of the merged build on macOS found a crash that unit tests had not (a navigation with no source frame; see "Found by running the app" below). It was fixed.
7. `gitleaks` was run on the public tree and history. Dependencies were listed and license-checked (see below).

## Threat model

The attacker is one of:

- **A malicious website** trying to reach native code, spoof the address bar, write files, open apps, use the camera or microphone, or run a command through the terminal feature.
- **A malicious or compromised update server or filter-list server** trying to deliver code, make the app fetch from the local network, or exhaust memory.
- **A malicious file** (bookmark import, saved session, places database, zip) trying to crash the app, grow memory, or turn into a command.

Out of scope: an attacker who already runs code as the same user on the Mac; WebKit vulnerabilities themselves (Wyvern uses the system WebKit; keep macOS updated); physical access.

Severity is the reviewing agent's own judgement, not a CVSS score. "Not fixed" rows say why.

## Found by running the app

Unit tests passed, but the first real launch of the merged build crashed on its first navigation: one of the sweep fixes read `navigationAction.sourceFrame.request`, and WebKit passes a nil source frame for loads the app starts itself even though the Swift type is not optional. ## Defenses that were already in the code, and why they are built that way

### Web content

Each line is the evidence. The next sentence is why the defense is built that way.

- `javascript:` and `data:` are cancelled for every frame (`NavigationPolicy.swift:151`). Those schemes execute script or render attacker HTML, and text typed in the bar becomes a search instead (`InputResolver.swift:45-46`).
- `blob:` and `about:` are allowed (`NavigationPolicy.swift:148-149`). Blob is a normal same-document URL, and `about:blank` is the empty document; when there is no host the field shows the absolute string, scheme included (`InternalPage.swift:105`).
- `icarus://` and `wyvern://` are cancelled (`NavigationPolicy.swift:156-158`). A page must not start a terminal command, and there is no run URL handler.
- External schemes ask only for a main-frame navigation (`BrowserTab.swift:771-775`). A real subframe must not open another app; a nil target frame is a top-level `window.open` and still has to pass the shell-option policy.
- `file://` loads only when the person opened that file, and `loadFileURL` is limited to its parent directory (`BrowserTab.swift:346-349`). Relative CSS and scripts of a typed page need that directory, and `allowFileAccessFromFileURLs` / `allowUniversalAccessFromFileURLs` are never set.
- A subframe never starts a download (`NavigationPolicy.swift:171-174`, `BrowserTab.swift:723-730`). Hidden frames must not write files; a nil target frame is not treated as the main frame for downloads.
- The Content-Disposition type is the token before the first semicolon (`NavigationPolicy.swift:185-187`). Filename parameters must not hide or invent `attachment`.
- Collisions use `name (n).ext` and reserve the `.download` sibling (`DownloadNaming.swift:63-73`). Two saves of one name must not overwrite each other or the in-progress file.
- Finished downloads get `com.apple.quarantine` `0083;…` (`DownloadNaming.swift:148-149`, `DownloadManager.swift:409-417`). `0083` means the file is not yet user-approved, so a later open still goes through Gatekeeper. `LSFileQuarantineEnabled` is also set (`Resources/Info.plist:29-30`).
- A main-frame attachment downloads even when the navigation was not a link click (`NavigationPolicy.swift:164-179`, `userInitiated` is unused). The person navigated to that document; subframe attachments stay silent. `NavigationPolicyTests.testResponseRules` locks this in.
- A user-chosen save name is rejected when it is empty, `.`, `..`, `/`, or contains a slash or backslash (`DownloadManager.swift:150-154`). The save panel is the person's choice, but it still cannot escape the folder.
- Camera and microphone prompts require `https`, or `http` on `localhost` / `127.0.0.1` (`MediaPermissionPolicy.swift:61-74`). Other origins are denied with no prompt, so an insecure page cannot ask for a device.
- Allow Once grants and stores nothing; Don't Allow does not persist (`MediaPermissionPolicy.swift:122-129`). A one-time answer must not become a standing permission. Always Allow is stored per origin key.
- Location and notifications cannot be granted (`SitePermissionPolicy.swift:36-42`). WKWebView has no public prompt for them, so a saved Allow still cannot turn the page's request on. There is no geolocation, notification, or clipboard delegate.
- `javaScriptCanOpenWindowsAutomatically` is false (`BrowserTab.swift:112-114`). Scripted `window.open` without a user gesture stays blocked; a gesture still reaches `createWebViewWith`, where Block and the burst cap apply. Ask creates the view; only Block refuses (`SitePermissions.swift:70-73`).
- Favicon hrefs are fetched only when the host matches the page and an https page does not pull http (`FaviconPolicy.swift:45-53`). The link is an image request, not script, and must not become a cross-site or mixed-content fetch.
- The bench message handler ignores its body and is installed only when `--wyvern-bench` is on (`BrowserTab.swift:175-177`, `BrowserTab.swift:874-882`). The probe only marks first paint, so page script cannot pass a command through it.
- The block probe runs in a named content world (`BlockListProbe.swift:24-27`). The page cannot call a main-world native function; posted strings are counted against the block list and are not loaded.
- `evaluateJavaScript` strings are a constant icon reader or a font size clamped to 12...24 (`BrowserTab.swift:272-284`). The script is not taken from the page, so the page cannot inject into the native call.
- `customUserAgent` is not set. `applicationNameForUserAgent` is Safari's own `Version/x.y Safari/605.1.15` (`SafariUserAgent.swift`), so the agent is identical to Safari's on the same Mac and does not publish an app-specific token a page could rely on or fingerprint. The version is read from Safari's `Info.plist` and accepted only as digits and dots.
- The address field uses `url.host`, so `userinfo@` is not the emphasized host (`InternalPage.swift:89-92`). The text the person trusts has to be the host that will be contacted. `InternalPageTests.testUserinfoIsNotTheDisplayedHost`.
- The inspector is on only when the setting is on and the surface is an ordinary web page (`DeveloperTools.swift:23-24`, `BrowserTab.swift:258-267`). New tab, bookmarks, settings, and the terminal stay closed, and the feature is off until the person enables it.
- Inspector selectors are used only after `responds(to:)` (`WebInspectorSPI.swift:9`, `WebInspectorSPI.swift:316-318`). A missing private method is skipped instead of raising. Developer-extras KVC is written only when a setter exists (`WebInspector.swift:14-16`).
- A terminal command is one argv element, `[shell, "-lc", command]`, with `environment: nil` (`TerminalBookmarks.swift:22-24`, `TerminalTab.swift:65-68`). The shell must be absolute and must not contain a newline or NUL (`TerminalBookmarks.swift:39-48`). The command is the bookmark the person stored, not a string from a page, a URL, or the clipboard.
- Import stores the bookmark disabled and unconfirmed (`TerminalBookmarks.swift:265-271`). An imported command cannot start until the person enables it, and `openTerminalBookmark` runs it only when `canLaunch` (`BrowserWindowController.swift:918-956`).
- Registered URL schemes are only `http` and `https` (`Resources/Info.plist:62-74`). `ssh://` and other external schemes never create a terminal tab. A handed-over `.url` file is loaded as a file in the web view (`AppDelegate.swift:502-508`), and the navigation policy still has to accept it.
- Restored and bookmarked `file` URLs are opened as documents the person already chose (`BrowserWindowController.swift:1271`, `BrowserWindowController.swift:3445-3447`). The grant is that file's directory, and it ends when the tab commits a non-file URL.
- There is no certificate-challenge handler and no per-host exception store (no `authenticationChallenge` / `serverTrust` in `Sources`). WebKit fails the load when the certificate is untrusted, and the app cannot remember a bypass.
- ATS sets only `NSAllowsArbitraryLoadsInWebContent` (`Resources/Info.plist:57-60`). Http pages can load inside the web view, while the app's own connections stay on ATS. There is no `NSAllowsArbitraryLoads` and no `NSExceptionDomains`. Certificate checks are unchanged.
- No app code enables mixed content. The web view keeps WebKit's default, which blocks active mixed content. The address lock is https-only, so an http document does not look secure.
- Browser-process logs are the software-rendering key names (`BrowserTab.swift:168-171`) and `WYVERN_DEVTOOLS_MODE` (`WebInspectorSPI.swift:247-250`). A page cannot put a URL, token, or document body into the log by navigating.
- There is no page context-menu delegate, no `registerForDraggedTypes` / `performDragOperation`, and no page-to-pasteboard bridge. The tab-strip menu is for tabs (`TabStripView.swift:68`). A drop or a page script cannot make the app launch a file or read the clipboard.
- Paste in the terminal is the person's Paste command (`AppDelegate.swift:631`). Nothing in navigation, bookmarks, or URL handling writes the pasteboard into the shell. Newlines in a paste are ordinary shell input.

### Network, updater, parsers

Each line is a defense that was already in the code, or that this sweep added, with why it is built that way.

- `Minisign.swift:33` and `Minisign.swift:130`: only legacy Ed25519 (`Ed`, bytes `0x45 0x64`) is accepted, and prehashed `ED` is refused. WHY: the signed bytes are the raw checksum file, which is what `minisign -l` produces, and a prehashed signature would not cover those bytes the same way.
- `Minisign.swift:154`: verification checks the file signature and the global signature over the trusted comment, and callers read the comment only from that result. WHY: an unsigned comment could otherwise claim a different version than the one the key signed.
- `UpdatePackage.swift:241`: the signature covers the `.sha256` file (hex plus file name), and the disk image must match that line. WHY: signing the small checksum file binds the image without streaming the whole disk image through the signature.
- `UpdateSource.swift:60`: a source is rejected when the key is missing or not a single minisign public key. WHY: with no pinned key, any signature would verify and the updater would have to be off.
- `Resources/Info.plist`: the update public key slot holds a placeholder in this public tree, and the build refuses to enable a built-in update source until a real public key is pinned. WHY: with no pinned key any signature would verify, so a source without a key is never accepted. The matching secret is never in the repository.
- `UpdateConfig.swift:43`: feed URLs are https, or dev-only http to a literal private IPv4 host when `WYVERN_DEV_UPDATER` is compiled in, and userinfo is refused. WHY: release builds must not fetch updates over cleartext, and the dev flag is how a private lab feed stays possible.
- `UpdateTransport.swift:10`: an https redirect may change host, and https never downgrades to http. WHY: release zips often live on a CDN, but a downgrade would drop the transport that the signature does not replace.
- `UpdateConfig.swift:121`: a candidate must be strictly newer by marketing version, then build. WHY: an equal or older signed package is a rollback, and a different commit at the same version is not treated as newer.
- `UpdatePackage.swift:145` and `UpdateZipInspector.swift:30`: the zip is capped at 500 MB and the declared unpacked size at 1 GiB, with at most 16 entries. WHY: the archive is untrusted until the signature check, so size has to be bounded before extract.
- `UpdateZipInspector.swift:16`: entry names must be the three expected root-level files, with no separators, `..`, absolute paths, symlinks, or directories, and the local header name must match the central name. WHY: `ditto` extracts by name, so a mismatch or a symlink would write outside the intended folder.
- `UpdatePackage.swift:306`: the extract directory is mode 0700. WHY: the unpacked disk image is not yet installed, so other accounts should not be able to read or swap it.
- `AppUpdater.swift:449`: the image is mounted read-only with `hdiutil`, and only one real `.app` directory is accepted (`AppUpdater.swift:487` uses `lstat`). WHY: a symlink or a second bundle would let the image choose what gets copied into place.
- `UpdateAtomicInstall.swift:64` and `UpdateAtomicInstall.swift:198`: the new app is checked with `codesign --verify --deep --strict` and an identifier requirement, before the swap and again after, and a failure puts the old app back. WHY: the minisign check covers the disk image, and the second check is what stops a bundle whose id or signature does not match after it is moved into place. Ad-hoc signatures satisfy the identifier requirement only; there is no Developer ID anchor.
- `AppUpdater.swift:493`: updater tools are argument arrays, not a shell. WHY: a hostile path in a feed must not be parsed as shell syntax.
- `AppUpdater.swift:51` and `BlockListController.swift:741`: update and list downloads use an ephemeral session with cookies off. WHY: a malicious server should not be able to plant cookies that later requests would send.
- `UpdateFeed.swift:48`: the feed body is capped at 1 MB. WHY: the feed is unsigned JSON or comments, so a huge body would be a denial of service before the signature is checked.
- `BlockListController.swift:45` and `BlockListController.swift:796`: a list download times out at 180 seconds and stops past 80 MB. WHY: the body is held in memory so it can be parsed once, and the cap is what keeps that bounded instead of streaming into an unbounded buffer.
- `HostsListParser.swift:107`: hosts parsing is line-based, not a regular expression. BOM and a leading `*.` are stripped, IDN labels are punycoded, and anything that is not `[a-z0-9.-]` is dropped (`HostsListParser.swift:244`). WHY: a domain that reaches the rule JSON has already been reduced to a hostname, so quotes and regex metacharacters never get there.
- `ContentRuleCompiler.swift:114` and `ContentRuleCompiler.swift:175`: the url-filter is a fixed template plus `jsonEscape(regexEscape(domain))`. WHY: even a label that passed the hostname check is escaped so it cannot break out of the JSON string.
- `ContentRuleCompiler.swift:26`: each `WKContentRuleList` is capped at 149,999 block rules plus one ignore rule, under WebKit's 150,000. WHY: one list over that cap fails to compile, so the compiler chunks instead of emitting a single illegal list. Several lists are intentional; the cap is per list.
- `BlockListModel.swift:590`: a cache file is compiled only when its SHA-256 matches the hash stored for that list, unless the hash is still empty. WHY: a swapped cache file would otherwise become rules without a new download.
- `BlockListController.swift:670`: a compile error that contains `://` is not shown. WHY: WebKit's error text can echo the rule, and that text must not become a clickable or logged URL.
- `BookmarkImport.swift:158`: imported bookmarks are kept only for http and https, at merge time. WHY: `javascript:` and `file:` in an HTML or JSON export must not become bookmarks that the browser will open later.
- `BookmarkHTMLParser.swift:6` and `BookmarkHTMLParser.swift:25`: Netscape HTML is parsed as text, never loaded in a web view, capped at 10 MB, and folders past depth 32 are flattened. WHY: bookmark HTML is untrusted and can contain script; a depth cap stops a nested-folder stack overflow.
- `BookmarkImport.swift:80`: titles are tag-stripped, controls removed, and cut at 512 characters. WHY: a title is shown in the UI and must not carry markup from the imported file.
- `BrowserFamilyBookmarkParser.swift:28`: Chrome-family JSON is capped at 10 MB before decode. WHY: the file is untrusted and the walker still has to hold the decoded tree.
- `SessionSnapshot.swift:11` and `BrowserWindowController.swift:1272`: a restored terminal tab stores only a bookmark id. The command runs only when that bookmark is enabled and `confirmedCommandHash` equals SHA-256 of its current command (`TerminalBookmarks.swift:157`). WHY: a tampered snapshot cannot supply a new command; it can only re-run one the user already confirmed.
- `TerminalBookmarks.swift:167`: terminal bookmarks are written mode 0600 by their own writer. WHY: the file contains commands that run as the user, so it should not be group-readable. The new `PrivateFile` path is used for the other application-support files.
- `Wyvern.entitlements:5`: the only entitlements are `com.apple.security.device.audio-input` and `com.apple.security.device.camera`. WHY: Hardened Runtime blocks the camera and microphone unless those keys are present, and the usage strings in `Resources/Info.plist:39` match the site prompts. No other entitlement was required by the code that was read.
- `project.yml:22` and `scripts/build-app.sh:118`: Hardened Runtime is on, the app sandbox is off, and the binary is ad-hoc signed with `--options runtime` and a designated requirement on the bundle id. WHY: the terminal needs a real PTY, which the sandbox would block, and the designated requirement is what lets microphone permission survive an ad-hoc re-sign. `ENABLE_USER_SCRIPT_SANDBOXING` is the Xcode build-script sandbox, not the app sandbox.
- `Resources/Info.plist:57`: `NSAllowsArbitraryLoadsInWebContent` is set, and the app's own `URLSession` calls are not given an arbitrary-load exception. WHY: a page the user typed may be http, while update and list fetches stay on the default transport rules. Dev builds can add local networking in `scripts/build-app.sh`; release Info.plist does not.
- `UpdateSource.swift:96`: the custom update source is a validated URL and public key in UserDefaults. WHY: the key is public, so the keychain is not required, and a source without a key is never stored as usable.
- `AppUpdater.swift:243` and `AppUpdater.swift:587`: the log records the feed host and the key fingerprint, not the key, and `token=` is redacted. WHY: the log is on disk and should not become a copy of the signing key or a bearer token.
- `Package.swift:28`: SwiftTerm is pinned exactly to 1.11.2, commit `b1262db5b6bea699a8260a8c66999436c508ca56`. WHY: a later pin pulled a Metal shader that failed to compile, and an exact pin also keeps the OSC 52 behavior above from drifting. `Package.resolved` is not committed; `scripts/scan-resolved-licenses.py` checks it after a build.
- `scripts/check-licenses.py:45` and `THIRD_PARTY_LICENSES.md:7`: the license scan rejects the AGPL, LGPL, and GPL families, and the third-party notice records SwiftTerm 1.11.2 as MIT. WHY: the app is Apache-2.0, and a copyleft dependency would be a different license than the notice claims. Package pins were not changed.

## Known limitations (stated plainly)

- **Not signed with an Apple Developer ID and not notarized.** Gatekeeper will warn. The build is ad-hoc signed with the hardened runtime and a designated requirement on the bundle ID. See the README for the exact steps to open it.
- **No release signing key is shipped.** The release download has no built-in update source. The updater verifies a minisign signature against a key you supply for a source you choose. Until a real key exists, there are no signed official updates. Updater work is ongoing.
- **Signatures have no expiry.** A source that is still serving an old, still-validly-signed package that is newer than your install could offer it (S2-11).
- **Private WebKit Inspector SPI.** Developer tools use private WebKit methods. They are guarded by `responds(to:)` checks and may break on a macOS update. Opening the inspector is limited to http and https pages. Developer tools are off until the user turns them on.
- **Not sandboxed.** The terminal tab needs a real pseudo-terminal. The entitlements are camera and microphone only; the hardened runtime is on.
- **A public hostname that resolves to a private address** is not detected by the host policy (names are not resolved on purpose) (S2-12).
- **The disk image check has a small time window** between the final hash check and the mount (S2-09). `ditto` can write an expanded member into a private 0700 folder before the size check removes it (S2-10).
- **The block-count badge can be inflated by a page** (S1-15). It is a counter, not a security signal.
- **No automated GUI or launch test** ships in this repository. Visual checks were done by hand-driven captures.
- Visual and layout fixes (flashing, artifacting) were reviewed by reading code and by one short driven run; not every case was exercised.

## How to verify

- Run the unit tests: `swift test` on macOS (requires the Xcode command line tools).
- Read the fixes: each finding names a file, and the commit history is public. Search the tests directory for the test named in the table.
- Run `gitleaks detect` on a clone (a config is included).
- Check a download: compare the SHA-256 printed in the release notes with `shasum -a 256` of the file you downloaded.
- Report anything you find: see [SECURITY.md](../SECURITY.md).
